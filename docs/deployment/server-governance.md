# 腾讯云服务器空间治理

更新日期：2026-10-27。

服务器只保留线上运行需要的内容、前一个可用版本、必要的数据恢复副本和有限的排障日志。每次发布成功后清理更早版本及重复构建产物，不靠长期堆积备份保障回滚。

**实施状态：本次一次性清理已完成；下述发布保留规则、镜像构建调整和日志总量限制尚未接入自动流程。写入本文不代表服务器配置已经生效。**

## 保留规则

前端和后端分别维护两版：**当前线上版本，以及前一个验收成功且可以回滚的版本**。不再按“最近七天”累计保留多个发布版本。

| 内容 | 保留范围 | 清理时机 |
| --- | --- | --- |
| 前端应用镜像和回滚材料 | 当前版和前一个可用版 | 新版本验收成功后，删除再往前的版本 |
| 后端应用镜像和回滚材料 | 当前版和前一个可用版；API、采集 worker、提示词分析 worker 的镜像需求一起核对 | 后端、相关后台页面及 worker 验收成功后清理 |
| 管理后台静态资源 | 当前版和上一版完整构建需要的资源 | 按构建清单删除更早且不再支持的资源 |
| 发布压缩包、重复源码副本、构建上下文、验收 HTML | 保留恢复流程实际依赖的一份工件，删除重复项 | 发布成功并确认回滚材料完整后立即清理 |
| 本项目可回收的构建缓存 | 不长期保留 | 构建结束且没有其他构建使用时回收 |
| 本项目已废弃的停止容器 | 无任务、数据和恢复用途的历史容器不保留 | 先核对用途及数据持久化，再按清单删除容器和旧镜像 |
| 失败发布的临时产物 | 保留最近一次失败的精简错误记录，不积累完整失败镜像和安装包 | 故障恢复完成后清理；不覆盖原有可用回滚版 |
| 业务数据、运行配置、任务和证书 | 保留当前有效内容 | 不能作为发布垃圾清理，具体范围见下表 |
| 运行日志 | 按容量和时间轮转 | 达到上限后淘汰最旧记录 |

“前一个版本”按发布单元独立计算。前端连续发布多次，不会因此删除后端唯一的回滚版本；后台随哪次后端发布更新，就记录对应的完整后台资源版本。多个服务共用同一个镜像 ID 时只存储一份。

版本是否可回滚，以验收和兼容性记录为准。不能直接把目录名最新的两个版本当作保留名单。

## 镜像有什么用

镜像可以理解为程序的运行包，里面包含程序代码、Node 或 Python 运行环境、依赖库，以及采集需要的浏览器等文件。容器根据这个包启动。当前版本的镜像用于日常运行和故障重启，上一版本的镜像用于发布失败时快速恢复。[Docker 镜像说明](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/)

**可以淘汰的是过期版本，当前运行和必要回滚依赖的镜像要保留。** 不再积累更早的历史版本，也不为同一个镜像长期增加一串 `rollback-*` 标签。

删除前要保护以下镜像：

- 所有在用容器及仍承担任务或恢复用途的停止容器所需的镜像。确认无用途的历史停止容器先按清单移除，再清理其镜像，避免旧容器永久保护废弃镜像。
- 当前及上一可用应用版本的镜像。
- Compose 和 systemd 任务实际使用的镜像。定时采集 worker 只在执行时出现，不能因检查时没有容器就删除其镜像。
- 证书续期等必要运维任务使用的工具镜像。`certbot/certbot` 只有在确认所有相关任务都不再使用时才可删除。
- 共享服务器上其他仍在使用的项目镜像。

镜像按明确清单删除，不使用全局 `docker image prune -a` 代替项目保留策略；该命令会覆盖没有容器引用的镜像，其中可能包括上述待执行任务需要的镜像。[Docker 清理说明](https://docs.docker.com/engine/manage-resources/pruning/)

### 解决镜像逐版变大的问题

现有前端发布脚本以旧应用镜像作为 `FROM`，先删除 `/app`，再复制新应用。后端在依赖未变化时也采用类似的增量路径。镜像由多层组成，新层中的删除操作不能把底层已经保存的文件从磁盘抹掉；反复在上一版本上叠加，会把历史应用层带进当前版本。[Docker 镜像层说明](https://docs.docker.com/engine/storage/drivers/#images-and-layers)

目标构建方式：

1. 前端从固定版本及摘要的 Node 运行基础镜像构建，只复制本次生产运行产物。仓库 `Dockerfile` 已有独立运行阶段，发布脚本也应采用这一思路。
2. 后端从固定的运行依赖基础镜像构建本次应用代码，不把上一业务版本作为持续叠加的基础。浏览器、字体、Python 依赖是否需要，由实际 API 和 worker 功能决定。
3. 新镜像独立构建并验收后，再删除更早的业务镜像及可回收缓存。不能为了腾空间提前移除当前版、上一可用版或构建正在使用的内容。

删掉旧标签不一定立即释放全部文件：当前镜像、上一版本或构建缓存还可能引用相同层。由 Docker 回收不再需要的层，不手动删除 `/var/lib/docker/overlay2`。

## 线上功能必须保留的内容

| 内容或路径 | 作用 | 处理要求 |
| --- | --- | --- |
| PostgreSQL、MySQL 等实际业务数据卷 | 用户、内容、任务及其他项目的业务数据 | 保留；数据卷不参与发布版本清理 |
| Redis 数据和持久化目录 | 队列及服务状态；不能笼统当作可清空缓存 | 保留，只有明确可重建的缓存键才能按业务规则过期 |
| `/opt/aigc-prompt/.env`、`runtime.env` | 数据库连接和服务运行配置 | 保留，限制权限；不放进文档、镜像或 Git |
| `compose.yml`、当前网关配置、后台 `dist` | 服务启动、路由及管理后台页面 | 保留当前有效文件及必要的上一版恢复材料 |
| `certificates`、共享入口使用的证书及验证目录 | HTTPS 和证书续期 | 保留，不能因为证书即将换新就提前删除 |
| `media`、`crawler-data` 中仍被页面、草稿或任务引用的文件 | 业务图片、采集结果和任务输入 | 保留；只有确认数据库已入库、远端副本可用且无任务或页面依赖的重复副本才能清理 |
| `browser-profile` | 采集平台登录状态 | 保留当前有效 profile；旧 profile 备份在当前会话验证可用后可淘汰 |
| systemd service、timer 及其脚本 | 定时采集和必要运维任务 | 保留有效定义及其依赖，不以“当前没有进程”为删除依据 |
| 发布锁和版本记录 | 防止并发发布、确定当前及上一版本 | 保留并沿用现有锁；文件很小，无需为省空间删除 |

`backend`、`frontend` 等宿主机目录目前仍被发布流程或挂载配置使用。可以去掉其中可重建的重复产物，但不能直接把整个源码目录删除。

这台服务器还运行博客等其他项目。未挂载的数据卷、旧项目目录先确认项目是否停用和数据是否有恢复价值，再决定删除；不能只根据 Docker 显示的“未使用”分类处理。

### 数据恢复副本保持最小数量

应用版本备份与数据库备份用途不同。目标是保留一份最新、已验证的数据库恢复快照；如果上一版恢复确实需要迁移前快照，再保留这一份。相同数据库备份不在多个发布目录重复复制。

替换旧快照前，先验证新备份可读取并做过对应恢复校验。数据库卷和同一系统盘上的 dump 不能替代独立于系统盘的恢复副本；重要数据应有至少一份独立且验证可恢复的副本。独立副本是否已具备，须在实施时核实，不能先删除唯一有效备份。

应用回滚通常继续使用现有数据库。不能为了切回旧应用自动导入旧 dump，覆盖发布后产生的新用户数据。涉及迁移时，先验证旧应用兼容性或准备明确的数据恢复步骤，再将其标为可用回滚版。

## 每次发布的处理顺序

1. 获取现有 `.release-deploy.lock` 和 `.backend-deploy.lock`，核对实际线上版本，避免与前后端发布或清理并发。
2. 记录当前版、上一可用版、镜像 ID、后台构建版本、配置及数据库迁移兼容性。新版本此时仍是候选版本。
3. 构建并发布候选版本，保留旧当前版及原有回滚材料。涉及后端时按既有流程协调 worker 和定时器。
4. 验证相关页面、健康接口、内容接口、后台资源和任务状态；确认必要 worker 与定时器恢复预期状态。前端发布还要检查旧页面访问静态资源的行为。
5. 验收成功后，将旧当前版记为上一可用版，新版本记为当前版。若无法保留可用回滚路径，停止淘汰原有回滚材料。
6. 根据两版记录生成删除清单，排除运行容器、任务定义、挂载目录、业务数据和其他项目仍需要的内容。
7. 删除更早版本的目录、镜像标签及镜像；使用精确路径和 ID，不强制删除被引用对象。清理保留目录内无恢复作用的重复产物，以及属于本项目的可回收缓存。
8. 复查磁盘、服务和保留材料，将释放空间及异常记入当前发布的简短验收记录。

失败发布不推进版本记录。先恢复服务，再移除失败候选的镜像和临时文件；最近一次失败仅保留精简诊断记录。清理失败单独报告，不把已验收成功的版本误报为发布失败，也不继续扩大删除范围。

上一版需要保存的是一套完整可用的恢复材料，不必重复保存压缩包、解压目录和全量源码副本。现有脚本仍依赖的备份文件，必须在恢复流程改造并验证后才能去重。GitHub Actions 的 artifact 保留期不会自动清理服务器上的 `releases`。

### 后台静态文件的清理

当前后台发布会追加 hashed assets，目的是让已打开页面和回滚版本继续读取旧 JS、CSS。治理后按当前及上一版的完整构建依赖清单保留资源，包含动态加载的文件、字体和图片，不能只检查 `index.html` 或文件日期。

比上一版更老的页面不提供无限期资源兼容；清理上线前验证旧页面能通过刷新恢复，且不会因强制刷新丢失未保存内容。没有完成该验证时，不能把删除旧资源描述为用户完全无感。

## 日志和构建缓存的上限

| 内容 | 目标规则 |
| --- | --- |
| AIGC 容器日志 | 沿用每个容器 `10m × 3` 的轮转设置，不无限增长 |
| systemd journal | 目标约 500MiB，最长 7 天，先达到容量或时间条件就淘汰旧记录；活动日志可能使实测值略高 |
| syslog 等其他系统日志 | 使用 logrotate，归档压缩，最长保留 7 天；每类归档预算 100MiB，超量时检查日志来源并调整轮转 |
| 发布日志和截图 | 当前及上一版本只留必要验收记录；失败发布仅留最近一次精简错误记录 |
| 本项目构建缓存 | 成功发布后不保留已可回收的缓存；镜像仍依赖的层由 Docker 管理 |

journal 的容量和保留时间分别通过持久配置中的 `SystemMaxUse`、`MaxRetentionSec` 控制，本次执行一次 vacuum 不会形成长期上限。[journald 配置说明](https://www.freedesktop.org/software/systemd/man/latest/journald.conf.html)

共享主机的其他容器日志也应逐服务补齐轮转；已有容器通常需要在对应发布窗口重建才能采用新的日志参数，不为本次文档重启整台 Docker。[Docker 日志配置说明](https://docs.docker.com/engine/logging/drivers/json-file/)

当前构建缓存由共享 Docker builder 管理。实施时先使用项目独立 builder 或核实缓存归属，再回收本项目可回收项；不能用一次全局 builder 清理处理其他项目尚在使用的构建资源。

## 空间检查和实施验收

系统盘达到 80% 时检查增长来源，达到 90% 时暂停新的发布和非必要写盘任务。只处理已明确可删除的对象，不通过删除业务数据绕过空间检查。完整镜像构建前至少预留 5GiB，并估算本次构建的峰值空间；不足时清理已确认垃圾或转移构建步骤，不能先删唯一回滚版本。

接入自动治理后应满足：

- 每个发布单元仅存在当前版和前一个可用版的恢复材料；更早版本和重复工件已清理。
- 当前版、上一版、定时任务和其他线上项目需要的镜像仍可用；旧标签不持续累积。
- 连续多次发布后，镜像大小及应用层数量不再随发布次数线性增长。
- 一次正常发布和一次失败回滚均验收通过，且回滚不覆盖业务数据库的新数据。
- 首页、后台、健康接口、内容接口和相关 worker 状态正常；清理本身不重启常驻业务容器。
- 数据卷、业务图片、登录 profile、运行配置和证书均未被版本清理删除。
- 日志限制重启后仍生效，清理失败有明确记录，磁盘释放量以 `df` 实测为准。

日常只读检查：

```bash
df -h /
sudo -n docker system df
sudo -n docker ps -a
sudo -n journalctl --disk-usage
curl --fail --silent --show-error --max-time 15 https://aigc-prompt.com/health
```
