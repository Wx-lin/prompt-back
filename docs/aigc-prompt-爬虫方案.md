> 最后更新：2026-10-09（替换为 MediaCrawler + 后台一键采集方案，此前手写脚本版本已废弃）
> 前置约束：本方案延续 `AGENT.md` 已确认的策略——**抓取 + 必须标注来源作者和跳转链接**，这是经过版权风险权衡的"概率可控的灰色操作"，不是合法方案。本文档只讨论技术实现，不改变这个已有的风险判断。

## 一、现状总览

当前采集能力：后台管理面板（`admin-panel/`）的"采集草稿"页提供**一键采集**入口，支持多选平台（小红书 / 微博 / 快手），点击后自动完成"拉起浏览器 → 搜索关键词 → 采集笔记/动态 → 下载图片 → 导入草稿表"全流程，运营方（你）只需要在页面上操作，不需要碰终端或写代码。

采集到的内容进入 `crawl_drafts` 草稿表，**不会自动发布**，必须经过人工审核（整理提示词原文、补全分类/模型标签），审核通过后才转为正式的 `Prompt` 内容。

## 二、技术原理

### 2.1 核心难点：平台的请求签名机制

小红书、微博、快手这类平台的接口请求都带签名参数（例如小红书的 `x-s` / `x-s-common`），这些签名由平台前端 JS 在浏览器里现场计算，用来识别"请求是否来自真实浏览器"。直接用 `requests`/`httpx` 发 HTTP 请求会被直接拦截。

业内两条技术路线：

| 路线 | 做法 | 优缺点 |
|---|---|---|
| **JS 逆向破解签名算法** | 逆向分析平台前端代码，重写签名计算逻辑 | 性能最好，但平台持续对抗升级，逆向代码要不断跟进维护，个人开发者成本高 |
| **浏览器自动化 + 复用登录态**（采用） | 用真实浏览器登录，在页面里直接调用平台自己的签名函数拿到签名，再用这个签名发请求 | 不需要逆向任何加密逻辑，平台改版通常不影响，缺点是比纯 HTTP 请求慢（要起浏览器） |

### 2.2 CDP 模式：遥控一个真实 Chrome，而不是无头浏览器

本方案进一步采用 **CDP（Chrome DevTools Protocol）模式**：不是启动一个全新的、一眼就能被识别出"不是人在操作"的自动化浏览器（比如 Playwright 默认的 Chromium 实例），而是**连接一个真实的、带完整登录态的 Chrome 窗口**，像人类操作一样控制它。

实测验证过默认 Playwright 浏览器会被小红书直接识别并拦截（返回"IP存在风险"提示），换成真实 Chrome + 真人登录态后恢复正常——这是本方案选用 CDP 模式而不是默认 headless 浏览器的直接原因。

### 2.3 一次采集的完整流程

```
运营方在后台点击"开始采集"（可多选平台 + 填关键词 + 数量）
  │
  ▼
后端（FastAPI）立即创建任务记录（status=pending），不阻塞，马上返回
  │
  ▼
后端后台依次（排队，不并行）为每个勾选的平台执行：
  1. 检查调试用 Chrome 是否已启动（没启动则自动拉起）
  2. 用子进程调用 MediaCrawler：
     uv run main.py --platform wb --keywords "关键词" \
       --crawler_max_notes_count 10 --get_media true
  3. MediaCrawler 内部：
     a. 通过 CDP 连接调试 Chrome
     b. 打开平台搜索页，输入关键词
     c. 对每条候选笔记：打开详情页 → page.evaluate() 执行平台的签名函数
        → 用签名发起真实数据请求 → 解析标题/正文/作者/互动数
     d. 把结果写入本地 jsonl 文件（data/{平台}/jsonl/）
     e. 若开启媒体下载：把配图/封面下载到本地（data/{平台}/media/{内容ID}/）
  4. 后端扫描新产出的 jsonl + 媒体文件，和数据库已有草稿做去重，
     把新内容写入 crawl_drafts 表
  5. 更新任务状态为 success/failed，记录新增条数和日志
  │
  ▼
前端每 3 秒轮询任务状态，完成后自动刷新草稿列表，运营方直接在"采集草稿"页看到新数据
```

### 2.4 为什么多平台采集是排队执行，不是并行

三个平台共用**同一个调试 Chrome 实例**（同一套登录态目录）。如果同时并行跑多个 MediaCrawler 子进程，它们会抢着切换浏览器里的页面/标签，互相干扰甚至采集到串台的数据。所以设计成严格排队：小红书跑完才开始微博，微博跑完才开始快手。前端对每个平台的任务单独轮询展示进度，运营方能看到"小红书已完成、微博采集中、快手排队中"这种独立状态。

### 2.5 技术选型：为什么最终用 MediaCrawler，而不是自己重写

早期方案（本文档的上一版）建议"只参考 MediaCrawler 的技术思路，自己重新实现，不直接用它的代码"，理由是它的仓库声明"仅供学习研究，禁止商用"。

**后续决策变更**：用户已知情该许可证限制，明确选择直接使用 MediaCrawler（理由：其 CDP 模式 + 内置 WebUI 后端架构已经完整覆盖本项目需求，重写的性价比低，且"CDP 连真实浏览器 + 页面内取签名"这套思路本身是公开通用做法，非 MediaCrawler 独创）。**该风险判断由用户本人做出并承担，本文档如实记录这一决策过程，不代表本项目已获得商用授权。**

## 三、平台数据形态差异（必须如实知晓的限制）

MediaCrawler 支持小红书、抖音、快手、B站、微博、贴吧、知乎共 7 个平台，**不支持 X/Twitter**（技术限制，国内这类工具普遍没有可用的 X 直连爬取通道）。

按内容形态和本项目"AI提示词+效果图"的匹配度，当前只启用三个平台：

| 平台 | 内容形态 | 图片情况 | 备注 |
|---|---|---|---|
| **小红书** | 图文笔记 | 多张效果图，质量最匹配 | 主力平台 |
| **微博** | 图文动态 | 多张配图（需开启 `--get_media` 下载） | 内容量大，质量参差 |
| **快手** | 短视频为主 | 通常只有一张视频封面图 | 和"多张效果图"的产品形态不完全匹配，后台会明确提示运营方注意甄别 |

**三个平台的 MediaCrawler 内部数据落盘路径规则不统一**（已实测验证）：
- jsonl 文件用完整平台名：`data/{xhs|weibo|kuaishou}/jsonl/search_contents_{日期}.jsonl`
- 媒体下载目录用 CLI 简码：`data/{xhs|wb|ks}/media/{内容ID}/`

后端 `crawl_task_service.py` 已针对这个不一致做了专门适配（`jsonl_dir_name` 和 `media_dir_name` 分开配置），否则会出现"采集进程正常跑完、图片也下载成功，但扫描 jsonl 目录读不到数据"的静默失败——这个坑已经真实踩过并修复，详见代码注释。

## 四、系统架构

```
admin-panel/（Vite + React + TypeScript 后台前端）
  └── 采集草稿页：一键采集面板（多选平台+关键词+数量）、草稿列表、审核弹窗

app/（FastAPI 后端）
  ├── models/crawl_task.py      — 采集任务记录表（一个平台一条，batch_id 关联同批次）
  ├── models/crawl_draft.py     — 采集草稿表（人工审核前的原始素材）
  ├── services/crawl_task_service.py — 核心编排逻辑：拉起 MediaCrawler 子进程 + 导入草稿
  └── routers/admin.py          — /api/admin/crawl-platforms、/crawl-tasks、/crawl-drafts

MediaCrawler/（独立第三方项目，与本项目平级，NOT 本项目代码库的一部分）
  ├── 通过 subprocess 调用，不 import 任何代码（保持许可证边界清晰）
  └── CDP 连接调试用 Chrome（独立 profile：.chrome_debug_profile/）
```

**为什么不用 Celery/RQ 等任务队列**：采集是运营方手动触发、低频、单用户场景，用 `asyncio.create_task` fire-and-forget + 数据库记录任务状态就够用，不需要引入消息队列这类重型基础设施。已知局限：后端进程重启后正在跑的任务状态会卡在 running/pending，需要人工介入确认（这个场景出现频率低，可接受）。

## 五、风险提示

### 5.1 封号风险（必须如实了解）

**有真实风险，不是零风险**，风险等级因平台而异：

- **小红书**：风控最敏感。已实测验证默认自动化浏览器会被直接拦截；真实 Chrome + 真人登录态能正常使用，但高频/大批量采集仍可能触发滑块验证或临时限流。
- **微博 / 快手**：目前测试下（单次 10 条/平台）未触发明显风控，但不代表没有阈值，长期高频使用风险会累积。

即便用的是目前最接近"人类操作"的 CDP 真实浏览器方案，平台仍然可能从**行为模式**上识别自动化：请求间隔过于规律、短时间搜索量远超正常用户、同一账号长期固定批量操作等。

**已有的防护措施**：
- MediaCrawler 内置随机延时（`CRAWLER_MAX_SLEEP_SEC`）
- 当前默认单次采集数量保守（10条/平台）
- 用独立调试 Chrome profile，不会污染日常使用的账号

**强烈建议（运营方自行决策和承担）**：
1. 登录的账号使用小号，不要用主力/实名账号
2. 保持低频采集（例如每天 1-2 次，而非高频批量跑）
3. 不要把单次采集数量调得过大

### 5.2 版权与合规风险

1. 本方案的所有技术实现都建立在"概率可控的灰色操作"这个已有共识之上，**技术上能跑通不等于零风险**。
2. MediaCrawler 本身的许可证是 `NON-COMMERCIAL LEARNING LICENSE 1.1`（仅限学习研究，禁止商用），本项目用户已知情该限制并自行决策使用，该风险由用户承担，不代表本项目获得商用授权。
3. 必须严格落实"标注来源 + 举报下架渠道"（`ContentReport` 表，P0功能），这是降低版权风险的关键缓解措施，不能省略。
4. 所有采集内容进入草稿表后**必须人工审核**才能转为正式内容，不允许自动化全流程直接发布。

## 六、使用方法（给运营方）

### 首次使用前的准备

1. 调试用 Chrome 需要分别打开小红书、微博、快手网页版登录一次（登录态永久保存在独立的 `.chrome_debug_profile/` 目录里，之后不需要重复登录）
2. 确保后端服务（`uvicorn app.main:app`）和前端服务（`admin-panel/` 的 `npm run dev`）都在运行

### 日常采集操作

1. 打开后台"采集草稿"页
2. 在"一键采集"面板勾选需要的平台（默认全选三个）、填写关键词、设置每平台采集数量
3. 点击"开始采集"，页面会显示每个平台的实时状态（排队中 / 采集中 / 已完成 / 失败）
4. 采集完成后，新草稿自动出现在下方列表（默认筛选"待审核"）
5. 点"查看/审核"逐条整理提示词原文、分类、适用模型，确认无误后"通过并入库"转为正式内容
