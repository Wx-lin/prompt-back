## 摘要与阶段判断

AIGC 提示词站是一个以图片效果为入口的免费 AI 提示词图库。用户浏览或搜索效果图，查看提示词与来源，复制后在外部 AI 工具使用。平台的核心价值是减少寻找和整理提示词的时间；当前不提供站内图片生成或提示词交易。

项目已经具备可访问的主站、管理后台，以及“采集—草稿—审核—发布”的内容链路。公开列表接口在本次核验时返回 66 条已发布内容，中文与英文页面均可访问。当前更适合定位为已上线的内测 MVP：功能面已成形，但采集稳定性、内容授权、数据标签完整度和真实用户转化仍需持续验证。

必须区分三个层次：源码存在某项能力，说明它已实现；当前线上请求成功，说明该入口在核验时可用；持续稳定运行或业务有效，必须有连续执行记录和用户数据支持。本次没有获得服务器登录或有效管理员会话，不能确认今天的定时采集是否成功，也不能将新增内容数量归因于自动采集。

## 产品定位与使用场景

目标用户包括刚接触 AI 绘图的用户、需要头像或封面素材的内容创作者，以及寻找风格灵感的 AI 绘画使用者。现阶段优先解决“找到可参考的效果图和对应提示词”，而非解决模型调用、算力供给或商业交易。

| 用户任务 | 当前产品承接方式 | 边界 |
| --- | --- | --- |
| 找到适合场景的图像风格 | 瀑布流、分类、模型筛选、关键词搜索与排序 | 模型标签尚不完整，首页模型候选列表仍来自演示数据 |
| 查看并复用提示词 | 详情页与详情弹层、多图查看、一键复制、来源展示 | 展示效果不保证不同模型或参数下可复现 |

| 持续补充内容 | 手动采集、定时计划、草稿审核与发布 | 平台登录、人工验证和网络限制影响采集 |

## 前端架构与体验

主站采用 Next.js 16、React 19、TypeScript 和 next-intl。首页在服务端获取内容与会话，并根据 URL 条件获取首屏和筛选结果；客户端负责条件交互及后续分页无限加载；分类、模型、搜索及排序条件写入 URL，便于分享和恢复浏览状态。详情支持独立 URL 与拦截式弹层，兼顾直接访问和连续浏览。

| 层次 | 当前实现 | 产品意义 |
| --- | --- | --- |
| 页面与交互 | 图库、详情弹层、独立详情、登录、收藏；移动端适配与主题切换 | 支持从发现到复制、保存的连续路径 |
| 浏览器侧接口层 | Next.js Route Handlers 组成 BFF，转发必要的浏览和鉴权操作 | 浏览器不必直接连接内部 FastAPI 地址 |
| 会话 | 后端签发 JWT，BFF 使用 HttpOnly Cookie 保存；生产环境启用 Secure 与 SameSite=Lax | 减少浏览器脚本直接读取用户访问令牌的机会 |
| 数据请求 | 公共服务端读取允许 60 秒缓存；携带用户令牌的读取使用 no-store；设置请求截止时间 | 平衡内容加载和用户数据隔离 |
| 搜索入口 | 标题与描述关键词搜索；分类、模型和排序组合 | 便于按具体用途找到内容 |
| 搜索引擎入口 | metadata、canonical、Open Graph、robots、sitemap | 为内容页面被检索和分享提供基础条件 |

当前前端仍有四项明显限制。第一，首页模型候选列表仍从 demoPrompts 提取，详情推荐列表仍使用 demoPrompts；主图库和详情主体在生产环境读取真实后端。第二，组合搜索的部分过滤和排序通过服务端逐页拉取结果后处理，内容规模增长会增加请求成本。第三，sitemap 当前最多拉取 250 条内容，尚不是可持续覆盖全量内容的方案。第四，登录后返回原浏览位置、英文路径恢复，以及点赞、收藏、复制失败的可见反馈仍可完善。

后端虽有同分类推荐接口，当前前端并未完整使用它；这也不属于语义检索或个性化推荐系统。源码中的图片下载入口和分享能力，不代表所有浏览器与外部图片地址都已完成兼容性验收。

## 后端、数据与服务边界

后端采用 FastAPI、Pydantic、异步 SQLAlchemy、PostgreSQL、Redis 与 Alembic。路由层负责鉴权和输入输出，服务层处理内容、审核和采集逻辑，数据库保存可长期追踪的内容和任务状态。

| 数据对象 | 主要职责 |
| --- | --- |
| Prompt / PromptImage | 正式提示词、分类、模型标签、效果图、作者来源、发布状态与互动计数 |
| User / Interaction | 用户身份及点赞、收藏关系 |
| CrawlDraft / 草稿图片 | 原始采集内容、来源平台、原内容 ID、图片和人工处理状态 |
| CrawlSchedule | 关键词、平台、每日时间、每轮数量、启停和自动发布选项 |
| CrawlTask | 单个平台的执行过程、阶段、错误、创建与结束时间和结果计数 |
| ContentReport / SearchLog | 内容反馈处理和搜索词聚合 |

后端支持分页、分类与模型筛选、最新/点赞/浏览排序、标题与描述模糊搜索；相似内容采用同分类规则。Redis 用于验证码、热词和浏览量等临时或聚合数据；应用内部另有刷新热词、回写浏览量的任务，它们与服务器上的采集定时器是两类不同任务。

用户身份支持邮箱验证码与 Google ID token 校验。邮箱验证码发送有间隔限制；实际邮件送达和 Google 登录依赖当前线上配置及第三方服务，本次未进行真实登录验收。

对外请求路径需要区分主站 BFF 与内部 FastAPI：公网网关将主站及其接口交给 Next.js，管理员接口单独转发至 FastAPI。因此，不应将源码中的全部 FastAPI 路径理解为公网直接暴露的接口。

## 内容采集、审核与发布机制

采集适配层目前配置小红书、微博和快手，通过独立 MediaCrawler 子进程读取平台内容，保存 JSONL 与图片，再按平台和原内容 ID 去重，形成采集草稿。快手当前主要导入视频封面图片，不能表述为完整的视频内容库。

内容链路为：选择平台、关键词与数量 → 获取平台登录状态 → 采集与去重 → 写入草稿 → 人工处理或 AI 自动审核 → 正式提示词及图片入库 → 主站展示。自动发布只处理本轮新增草稿，不批量处理全部历史积压草稿。

| 路径 | 审核和发布行为 | 失败处理 |
| --- | --- | --- |
| 采集草稿的人工审批 | 人工指定正文与分类；存在版权关键词规则；AI 预审作为建议 | AI 服务异常可降级，由人工决定是否通过 |
| 开启自动发布的采集计划 | 先处理图片存储，再进行结构化多模态审核；要求有效标题、提示词和可信 AI 图片；只发布认可的图片 | 图片、模型或输出格式异常时保留 pending，记录待处理原因 |
| 计划页面的立即执行 | 使用该计划当前的自动发布设置 | 沿用该计划的审核与失败处理行为 |
| 普通手动采集 | 生成草稿，供后续处理 | 不应默认理解为与自动发布计划相同的流程 |

AI 审核实现使用百炼 OpenAI 兼容接口，当前源码指定 qwen3.7-plus，并校验结构化字段、分类、布尔值及图片索引。它承担内容相关性判断、图片可信度判断、文案整理和分类，不承担内容授权证明，也没有本次可核验的审核准确率、误判率或稳定调用成本。

人工审批与自动发布的规则并未完全统一：自动路径未调用人工路径中的版权关键词过滤。因此，不能宣称所有内容都经过同一套版权硬拦截；标注作者与来源也不能代替授权。下一阶段应统一规则、保留证据并完善申诉和下架处理。

## 管理后台与定时运营

管理后台使用 React、Vite 与 TypeScript，源码包含内容管理、采集草稿、举报处理和定时任务四个模块。内容管理覆盖创建、编辑、发布、下架与删除；采集草稿页面支持平台多选、关键词与数量设置，登录失效时读取任务状态并展示扫码辅助窗口。

定时任务支持北京时间每日多个时间点、每平台每轮 1–50 条、关键词、平台、启停、自动发布和立即执行。服务器 systemd 定时器每分钟检查数据库中的到期计划，实际采集频率由计划设置决定；每分钟检查不意味着每分钟采集。

10 月 10 日发布时确认的默认配置为：小红书每天 10:00 与 22:00、每轮 20 条、AI 审核通过后发布。该配置是历史已验证快照，本次无法确认它是否已被修改。

任务记录区分排队、采集、等待扫码、AI 审核、完成和失败；展示新增草稿、发布与待人工处理数量，并提供错误原因及日志。按日统计使用北京时间，但当前按任务创建时间归属日期；统计单位是单个平台执行任务，不一定等于一轮计划或一次用户点击。

跨进程锁用于避免采集并发；排队任务可由调度器继续处理。原执行进程丢失后，调度器记录中断失败并保留既有内容。它不是无条件重试平台失败的机制，也不是可以抵消平台限制的方案。

后台二维码接口需要管理员鉴权，并校验任务阶段和有效期。登录状态保存在服务器私有浏览器目录。此前已实测弹出小红书二维码，也遇到扫码未完成和平台人工安全验证；“二维码能显示”不能据此推断“登录成功”或“采集成功”。本次没有验证今日扫码与定时采集结果。

## 质量证据与已知限制

本次本地后端 pytest：62 项通过、1 项跳过；被跳过的是需要独立 PostgreSQL 测试数据库的集成测试。前端 Vitest：9 个测试文件、42 项测试通过；TypeScript 类型检查通过。此前采集与定时模块的专项测试记录达到 88% 覆盖率，该结果不代表当前全仓库覆盖率。

上述检查证明所覆盖的本地逻辑能按测试预期执行。COS、模型服务等测试包含模拟依赖；本次未执行完整浏览器 E2E、生产数据库恢复测试、真实邮箱/Google 登录或真实多平台采集验收，不能将本地通过扩写为生产全链路通过。

| 当前限制 | 对产品的影响 | 下一步建议 |
| --- | --- | --- |
| 登录状态可能失效，平台可能要求人工验证 | 定时到点也可能无法补充内容 | 核对任务日志、完善待登录提示及失败通知，建立人工接续流程 |
| 自动与人工审核规则存在差异 | 内容处理标准不完全一致 | 统一来源、版权声明及发布规则，保留人工复核记录 |

| 详情推荐和首页模型候选列表仍使用演示数据 | 页面与真实内容库之间存在偏差 | 接入真实分类/模型目录及后端推荐，避免演示内容进入正式浏览路径 |
| 组合搜索逐页拉取、原图复作缩略图 | 内容量增长后增加请求与图片加载成本 | 将组合检索下推到后端，建立缩略图处理与缓存策略 |

## 下一阶段产品与研发重点

近期优先验证运营闭环：确认最新计划配置及每天真实执行结果；区分未登录、人工验证、采集为空、审核未通过和系统异常；让需要人工处理的任务可被发现并接续。没有可靠内容供给时，不宜仅通过增加采集次数扩大规模。

第二步完善内容质量与前端一致性：补全模型标签、清理演示推荐、统一审核规则、保留来源信息和处理记录，并验证复制、登录和收藏关键路径。用户应能够理解内容来源、适用模型与失败原因。

之后再围绕真实数据扩展：优化组合搜索与缩略图，扩展 sitemap，完善运营权限、备份恢复和业务统计。个人化推荐、用户投稿、站内生成或付费功能属于后续产品选择，本次没有将它们列为已经实现的能力或确定交付承诺。

建议持续观察五组指标：用户浏览到复制的比例；搜索后复制或收藏的比例；内容的标签及来源完整度；到期任务执行、登录、采集、审核和发布的分阶段结果；申诉处理与下架时效。每项指标都应写清统计口径，不能把任务显示完成与实际获得有效内容混为一谈。
